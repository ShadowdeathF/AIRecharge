# 企业协议价、成本对账与利润分成设计

日期：2026-11-02。状态：设计评审稿，等待用户确认后实施。

## 1. 需求与已核实事实

用户已确认：

- 散客使用现有商城；不同合作公司的成交报价不同，企业收入不能直接套商城零售价。
- 企业业务同时存在商城下单和线下成交两种来源。
- 成本随时间或交易变化，需要纳入对账。
- 利润分成沿用用户新写的计算器；分成和风险支出需要独立菜单。

当前代码核实：

- 实际商城仓库是 `D:\projectcode\Orion-Key`，起点提交 `62e3d2c`；不是同名 GitHub 仓库对应的本地 `AIRecharge` 工作台。
- 对账表当前只有付款时间、订单、渠道、订单金额和状态。`WorkbenchQueryRepository` 汇总 `Order.actualAmount`；没有成本、企业报价、利润或渠道结算到账字段。
- 对账菜单实际跳转到 `/admin/dashboard#workbench-ledger`。现有 `/admin/risk` 管理订单安全风控。
- 直购、购物车下单分别调用零售/阶梯批发价格计算；首页商品来自匿名服务端请求。企业价格必须同时接通商品展示、购物车和服务端订单计算。
- 卡密、导入批次已有可追溯关联，但当前没有进货成本字段。
- 规则来源为 `D:\projectcode\AIRecharge\profit-calculator.html`，其 12 项计算测试已通过；原计算器只列出四个 GPT 套餐，正式功能须支持商城实际商品及规格，包括 Claude。

## 2. 方案取舍

1. **只给对账表加手填成本和收入**：改动最小，但不能满足企业在商城按专属价下单。
2. **只改商城企业会员价**：可覆盖线上企业订单，但线下成交仍需另记，利润容易漏算或重复。
3. **企业协议价 + 统一交易台账**：线上订单自动汇入，线下企业交易录入同一台账，以每笔收入和成本快照计算利润。能覆盖用户确认的两种来源，推荐采用。

用户已选择业务范围为“两种情况都有”；第 3 项的技术组织、下文的结算限制与优先级是本设计的建议，尚未作为已获批准的规则执行。

这是一项跨前台定价、订单、财务和分成的功能，复用现有 Next.js、Spring Boot、JPA 与 PostgreSQL，不增加新的业务系统或支付服务。

## 3. 企业与协议报价

- 后台维护企业和关联账号；同一企业可关联多个现有用户，一个账号在同一时间归属一家企业。归属只能由管理员设置，注册或下单请求不能自行指定企业。
- 协议报价按“企业 + 商品 + 规格”保存。多规格商品按具体规格报价，月付报价不得套到年付规格。
- 报价变更保留版本和操作记录，仅影响变更后的新订单。已创建的待付款订单在既有有效期内继续采用原成交价，重新支付也不重新计价。
- **建议价格优先级**：有效企业协议价优先；没有该商品/规格协议价时走现有零售/批发规则。协议价不再叠加批发折扣，页面清楚标示实际采用的价格来源。
- 线上商品、详情、购物车、结算须显示同一套价格。创建订单由后端根据登录账号重新计算，不信任客户端传来的企业 ID、单价、成本或利润。
- 展示价与提交下单时的有效报价发生变化时，返回价格变更提示并让客户重新确认，不静默按另一金额扣款。已创建订单的价格冻结与此区分。
- 匿名首页与公共缓存继续使用公开价格；企业登录后请求自己的价格数据。私人价格响应禁止被共享缓存；退出或换账号立即清除企业价格。
- 企业身份、名称、商品与规格名称、成交单价、数量、报价版本在下单时保存快照。账号换企业或商品改名后，历史订单仍能还原。
- 企业资料停用后阻止新的企业交易，操作前显示影响的账号；历史交易仍可查。恢复交易须由管理员处理，不能静默改用另一企业的报价。

## 4. 统一交易台账与收入

对账报表成为独立页面 `/admin/reconciliation`，区分“散客线上、企业线上、企业线下”。

- 线上已付款订单汇入台账，一笔来源订单最多对应一笔财务交易；保留原订单详情入口。
- 线下录入企业、业务日期、外部单号、商品规格、数量、实际成交单价、推荐人及备注；支持同单多种商品。
- 企业报价作为线下录入的默认值，允许本次特殊成交价覆盖，但须留原因，不反向覆盖企业报价。
- 线下交易是财务记录，不伪造支付回调、支付链接或自动发货，也不再次扣减已经交付的卡密。
- 若线下记录对应已有平台订单，应绑定并补充该订单的财务记录，不能新增第二笔销售收入。
- 手工新增支持幂等提交；CSV 导入先预览校验，按“企业 + 外部单号”识别重复，报出行号与冲突，不靠金额或商品名称猜测合并。

金额分开保存和展示：

| 金额 | 含义 |
| --- | --- |
| 商城参考价 | 商品当前公开价格，仅供参考，不用于改写历史成交收入 |
| 成交应收 | 本笔成交单价 × 数量，多商品求和 |
| 已收金额 | 已确认收到的客户付款；支持登记未收、部分收款和最终确认 |
| 支付订单金额 | 线上支付原始事实，只读，不被财务修改覆盖 |
| 订单成本 | 本笔各商品的实际单位成本 × 数量之和 |
| 已确认利润 | 最终确认的客户实收 − 已确认成本 |

本次“实收变化”主要解决不同企业的成交价，不把银行/支付渠道到账当成已有能力。渠道手续费及渠道账单导入不在本次实现范围；如将来加入，必须单独存储，避免在实收和费用中重复扣减。

线上有效付款可确认客户已付款，但不表示支付渠道已结算。线下部分收款可记录进度，只有本笔收入结清或明确确认为最终收入后才可进入分成；最终实收与应收不同时必须填写差异原因。零元赠送可确认，空白金额不是零。

## 5. 动态成本与历史快照

- 默认成本按商品/规格维护，只用于新增交易的预填；本次不擅自把计算器中的示例成本写成所有商品的真实进货价。
- 每笔、每项均可填写实际单位成本和成本说明。默认值带“待确认”标记，财务确认后用于利润。
- 同商品可以出现不同成交价和不同成本；成本和报价修改均不联动刷新已确认历史交易。
- 旧订单、未知成本或未配置成本的 Claude 规格显示“待补成本”，利润显示未知，单列待补数量；不能按成本为零夸大利润或进入分成。
- 多商品按项核算成本，总收入以整单客户实收为准，不通过四舍五入后的平均单价反推总收入。
- 此版按单确认成本，预留现有卡密/批次关联用于追溯；自动按进货批次计算成本不作为当前已授权规则添加。

## 6. 分成计算口径

计算必须由后端权威执行，前端展示和导出使用同一结果：

1. 订单利润 = 已确认客户实收 − 已确认成本。
2. 公司预留 = 订单利润 × 10%；分成池 = 订单利润 × 90%。
3. 分成池中技术总监 40%、总经理 32.5%、财务总监 12.5%、推荐奖励 15%。折算为总利润的 36%、29.25%、11.25%、13.5%。
4. 推荐人可以是上述任一人员、其他人员或待分配；本人的奖励叠加本人基础分成。正式系统用稳定人员 ID 识别人，不以同名字符串当作唯一身份，也不把分成人员角色当作后台访问权限。
5. 亏损订单保留负利润，按同样比例冲减各项；不截断为零，不只统计盈利订单。
6. 使用精确十进制累计后统一四舍五入到分，保持计算器的负数舍入行为。多笔小额订单不能先逐笔舍入再累加。
7. 原计算器会展示分成尾差。建议正式结算单保留“公司预留基数”和“结算尾差调整”两行，由公司预留余额承担最后的分币尾差，使人员结果沿用计算器且资金总额守恒；调整额必须显式展示。
8. 舍入的计算边界为同一张原始结算单：同一人员的基础分成与奖励先以精确值合并，再舍入。之后补分配奖励或发生退款/成本调整时，以冻结原单及相关调整计算该组累计应付，减去此前已入账应付，只追加差额。原单本身保持不可变，差额在后续结算单中作为已算好的调整行入账，不在新单再次乘分成比例。不把每次新增奖励或调整独立舍入，也不回算无关结算单。

金额示例：利润 100 元时，公司预留 10 元、技术基础 36 元、总经理基础 29.25 元、财务基础 11.25 元、推荐奖励 13.50 元。未指定推荐人的金额单列待分配，不自动分给某一人员。

## 7. 独立菜单：分成与风险

新增 `/admin/profit-sharing`，内部采用“分成汇总 / 结算单 / 公司预留与支出”页签：

- **分成汇总**：时间与企业筛选、已确认利润、公司预留、分成池、每人基础分成、推荐奖励、合计、待分配奖励和亏损提示；支持追溯到订单。
- **结算单**：从已确认且未结算交易生成预览，确认后冻结参与交易、收入成本快照、人员、比例与金额；记录结算周期、操作者、确认时间和应付/已付情况。预览不转账，不触发自动付款。
- **公司预留与支出**：公司预留累计、已提交支出、尾差调整、可用余额；可登记实验支出、风险补偿及其他支出，填写日期、金额、说明和可选关联交易。
- 风险、实验等公司支出只扣公司预留，不重复扣人员分成；公司余额可以为负并清楚提示，按计算器语义保留。
- 此处“风险”指经营支出；原 `/admin/risk` 的订单安全风控保持现有职责。
- 公司预留来自已确认交易及其调整的 10%，每笔只计提一次，不因生成或查看结算单重复增加。区间报表区分期初余额、本期计提、本期支出/调整和期末余额；累计余额不受当前筛选条件误导。
- 公司支出草稿可编辑或撤销；已提交支出更正通过关联冲正/替代记录处理，不删除资金历史。提交与重试使用同一幂等标识，关联业务流水有唯一约束。

## 8. 确认、结算与调整

- 财务交易状态至少区分：待补收入 / 待补成本 / 待确认 / 已确认未结算 / 已结算。收款进度独立于这些状态，不能把部分到账直接当成已具备分成条件。
- 对账默认按业务日期筛选：线上为上海时区付款日期，线下为录入的业务日期；同时保留实际收款和财务确认日期。
- 分成候选按财务确认日期筛选，并提供“全部未结算”；旧交易在补齐成本并确认后进入当次待结算池，不因业务日期较早而被漏掉。
- 未结算记录修改收入、成本、推荐人或企业等财务字段后，撤销原确认，展示变更并要求再次确认；已结算记录禁止直接覆盖。
- 已结算退款、成本纠正等通过关联原交易的调整记录进入之后结算，保留原结算单。调整可正可负，仍按原交易的分成人员和规则处理，不能套用后来变更的比例或企业归属。
- 支出和收入退款不能重复记同一笔资金。退款减少销售收入；额外风险补偿计公司支出。关联交易和说明可追踪，界面和服务端校验阻止把同一调整重复提交。
- 重要操作采用事务、版本校验和幂等键；并发确认、重复点击和重复导入不能重复算收入、分成、支出或支付登记。
- 分成人员可在不同结算周期更换，周期内确定人员后以 ID 和姓名快照冻结。已结算的人员与比例不受后续编辑影响。
- 三个基础分成职位对应人员由管理员明确设置，在财务确认和结算预览中可见；缺失任一职位人员时不能确认最终结算。线上交易推荐人默认待分配，后台财务设置，不增加前台推广注册或邀请码业务。
- 待分配推荐奖励保留精确值与已入账金额，可以先结算已明确人员的部分；后续分配按原结算单该人员的累计精确基础分成与奖励计算差额。基础分成的业务比例与原始记录不变，尾差释放或补提需明示，不独立舍入后直接叠加奖励。
- 已付款后出现负应付，建议先保留该人员负余额，可抵后续应付；实际退回资金发生时，财务可登记收回金额、时间与流水，支持部分退回，不自动追款或转账。人员离职也不抹除这笔余额。收回分成只冲人员往来，不作为新增销售收入，也不再次计提公司预留。

## 9. 对账交互与导出

- 顶部展示已收合计、已确认成本、已确认利润、待收金额、待补成本笔数和未结算笔数，注明各自覆盖范围。
- 明细展示业务日期、来源、客户/企业、交易号、商品规格与数量、成交应收、已收、成本、利润、推荐人、确认/结算状态。
- 查看侧边详情完成商品逐项核算、收款记录、成本确认、推荐人设置及修改历史；手机端保留关键金额，详情承载长字段，不将所有列强行塞进屏幕。
- 企业与报价、默认成本放在对账页面的辅助页签，不扩展无关 CRM 功能。
- CSV 与页面采用相同筛选、权限和金额算法，包含企业、来源、成本、收入、利润及财务状态；分成结算另有可追溯导出。
- 经营分析保留原来的销售趋势和订单钻取。涉及“销售额、利润、客户实收、渠道到账”的指标明确命名与口径，不继续把订单金额表述成渠道已结算金额。

## 10. 数据与接口边界

新增企业与报价版本、默认成本、财务交易及明细快照、收款记录、财务变更/调整记录、分成人员、结算单/明细、公司支出等必要持久化结构；命名与具体拆表由实施计划决定，不创建通用账务框架。

- 财务交易通过来源订单 ID 唯一绑定线上订单；手工企业交易保留企业、外部单号和幂等键。
- 企业归属、报价来源和成交价在服务端订单事务内写入快照；身份来自验证过的当前账号。
- 查询和修改使用现有统一响应包装、管理员鉴权与操作日志。报价、成本和分成结果不得泄漏给无权限账户。
- 审计至少包含操作者、修改时间、原因、字段前后值和关联记录；不记录密码、令牌、支付私密链接或卡密内容。
- 首次迁移保留旧订单金额，不猜企业身份、历史成本或推荐人，也不自动制造已结算记录。已付款历史订单以待补成本/待财务确认方式逐步核算。
- 使用可审查、可重复验证的增量 PostgreSQL 迁移，不能仅依赖生产环境的 `ddl-auto=update`。上线前先备份，不在设计阶段改远程数据库。

## 11. 实施与验收边界

按依赖分步完成：企业与报价及线上价格一致性 → 双来源对账、收款、成本确认 → 分成/公司支出/结算与审计 → 迁移和页面验证。各步仍属于同一功能交付，不能只交付一个静态计算器页面。

必要验收：

- 计算器原有 12 组规则在后端有对应精确计算断言，包含亏损、未分配推荐、公司余额为负和尾差。
- 两家企业对同 SKU 使用不同价格；匿名/散客沿用既有规则；公司 A 无法获取公司 B 的报价，也无法通过请求伪造公司。
- 首页、详情、购物车、直购与购物车下单价格一致；既有订单重付保持原价；修改默认价不重算旧订单。
- 同一 SKU 不同数量、成本和成交价正确累计；多规格和混合购物车正确；未知成本不算零。
- 线上、线下交易均可查询、筛选和导出；绑定平台订单、重复导入和重复提交不会重记收入。
- 未收与部分收款不提前分成；最终实收差异需要原因；补成本和修改后重新确认不会漏进待结算。
- 并发结算不能重复领取同一交易；公司支出只扣一次；已结算单不可变；后续调整只影响后续结算。
- 0.05 元利润先结技术基础、后补技术推荐奖，累计技术应付须与原计算器一次计算的 0.02 元相同，不多付一分钱；已付分成后的退款产生可追溯负余额，实际收回不会增加销售收入。
